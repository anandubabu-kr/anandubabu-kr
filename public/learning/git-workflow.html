01 · Git basics

How Git thinks

A commit is a full snapshot of your project, linked to the commit before it.

DistributedEvery clone is a complete repository with full history. You can commit, branch and diff offline.
Content-addressedEach commit is named by a hash of its content and parents, so history can't change silently.
Cheap branchesA branch is a tiny file pointing at one commit. Creating one costs nothing.

The everyday commands

Start or copy a repository git init · git clone <url>
See what changed git status · git diff
Stage only the hunks you mean git add -p
Record a snapshot git commit
Read the history git log --oneline --graph --all
Create and switch to a branch git switch -c feature/login
Get the team's latest work git fetch · git pull --rebase
Share your branch git push -u origin feature/login

A branch is just a pointer

main and feature/login are labels that point at commits.

HEAD is where you are: the branch you have checked out (shown as HEAD→).

Committing moves the current label forward. Nothing is copied.

Merge or rebase?

git merge

  • Joins two histories with a merge commit
  • Keeps the true record; never rewrites commits
  • Use for shared branches and PR merges

git rebase

  • Replays your commits on top of the latest main
  • Linear history, but creates new commit hashes
  • Use to update your own branch before a PR
Golden rule: rebase your own local work freely. Never rebase commits that others have already pulled.
02 · Branching strategies

Four common strategies

Strategy How it works Best for Watch out for
Git Flow main + develop, plus feature, release and hotfix branches Versioned releases, several supported versions Heavy process; long-lived branches drift
GitHub Flow main is always deployable; short feature branches merged by pull request Web apps and services with continuous deployment Needs solid CI and fast reviews
Trunk-based Everyone integrates into main at least daily; feature flags hide unfinished work High-velocity teams and monorepos Requires feature flags and strong tests
Release branches Cut release/x.y from main; fixes land on main and are cherry-picked back Products where customers run older versions Back-porting discipline

03 · Commit conventions

Conventional Commits

<type>(<scope>): <subject>

<body: what changed and why>

<footer: BREAKING CHANGE / Refs>
  • Subject in the imperative: “add”, not “added”
  • About 50 characters, no trailing period
  • Body explains why; the diff already shows what
  • Enforce it with commitlint in a commit-msg hook
feat a new feature
fix a bug fix
docs documentation only
style formatting, no logic change
refactor restructure, same behaviour
perf performance improvement
test adding or fixing tests
build build system, dependencies
ci pipeline configuration
chore other maintenance
revert undoes an earlier commit

04 · Git at scale

When the repository gets heavy

Problem Tool Command
Large binaries: models, datasets, design files, videos Git LFS git lfs track "*.psd" "*.onnx"
Clone takes ages because of years of history Partial clone git clone --filter=blob:none <url>
You only work in one part of a monorepo Sparse checkout git sparse-checkout set services/api
CI only needs the latest code Shallow clone git clone --depth 1 <url>
Build outputs and generated files committed .gitignore dist/ build/ *.log → artifact store

Monorepo or many repos?

Monorepo

Gains

Atomic changes across services · one CI setup · shared tooling and code

Costs

Needs sparse checkout, CODEOWNERS and path-filtered CI to stay fast

Polyrepo

Gains

Small, fast repos · independent release cycles · clear ownership

Costs

Cross-repo changes need coordination; shared library versions drift

Sharing code between repos: prefer a versioned package in a registry. Use submodules to pin external code at an exact commit, or subtree when consumers shouldn't need extra commands.

Keeping Git fast

git maintenance start

Background prefetch, commit-graph and repacking, so fetch and log stay quick

core.fsmonitor = true

A file-system watcher makes git status fast on huge working trees

feature.manyFiles = true

Smaller index and untracked cache for repositories with many files

scalar clone <url>

Ships with Git: partial clone, sparse checkout and maintenance in one step

In CI: shallow fetch, cache LFS objects between runs, and trigger jobs only for the paths that changed.
05 · Problems & fixes

Everyday accidents

Problem

I committed to main instead of my branch

Fix
git branch feature/x
git reset --hard origin/main
git switch feature/x

Only if main isn't pushed yet

Problem

My last commit is missing a file

Fix
git add missed.ts
git commit --amend --no-edit

Already pushed? Make a new commit instead

Problem

I lost commits after a reset or rebase

Fix
git reflog
git branch rescue HEAD@{2}

Reflog keeps every move of HEAD for about 90 days

Team-level incidents

Problem

An API key was pushed to the repo

Fix
git filter-repo --path .env \
  --invert-paths
git push --force-with-lease

Rotate the key first. Add gitleaks to pre-commit.

Problem

A 3-week-old branch conflicts everywhere

Fix
git fetch origin
git rebase origin/main

Sync daily, split into smaller PRs, enable rerere.

Problem

v1.5 broke something. Which commit?

Fix
git bisect start
git bisect bad v1.5.0
git bisect good v1.4.0
git bisect run npm test

Binary search finds it in a few steps.

06 · Conflicts & tracking

Six habits that prevent conflicts

01

Small PRs, merged fast

A few hundred lines, reviewed within a day

02

Sync every day

Rebase on main each morning; small conflicts stay small

03

Clear ownership

CODEOWNERS and module boundaries limit overlapping edits

04

Auto-format everything

Prettier, Black or gofmt in pre-commit: no whitespace fights

05

Defuse hot files

Split giant configs; generate changelogs in CI, not by hand

06

Reuse resolutions

rerere replays a conflict fix you already made once
